# Встроенное самотестирование UAMenu

Касса умеет проверить себя сама: войти под заданным кассиром, прогнать
сценарий продажи, снять экраны и записать журнал. Всё управляется одним
файлом рядом с `UAMenu.exe`.

## Как включить

Положить рядом с exe файл `selftest.ini`. Образец —
selftest.ini.sample, достаточно
переименовать.

Файла нет — касса работает как обычно, ничего не меняется.

> Именно поэтому образец лежит как `.sample`. Если положить рабочий
> `selftest.ini` на боевую кассу, она будет уходить в самопроверку при
> каждом запуске.

## Что происходит при запуске

```
UAMenu.exe стартует
        │
        ▼
  есть selftest.ini?
        │ да
        ▼
  автовход: кассир, схема Oracle, сервер — из [Login]
        │
        ▼
  главная форма готова, база подключена
        │
        ▼
  прогон [Scenario]: товары, карта, баллы, снимки
        │
        ▼
  журнал и снимки в подкаталог с датой прогона
```

Автовход встроен в собственный механизм кассы: форма входа заполняет поля
и ставит `ModalResult = mrOk` — тот же путь, что и при `ShowLogin=0`.

## Файл сценария

### `[Login]`

| Ключ | Что это |
|---|---|
| `User`, `Password` | кассир из `TMS_CASIR` |
| `Schema`, `SchemaPassword` | схема Oracle и её пароль |
| `Server` | псевдоним базы из `tnsnames.ora` |

### `[Test]`

| Ключ | По умолчанию | Что делает |
|---|---|---|
| `OutDir` | `SelfTest` | куда складывать результаты |
| `Screenshots` | `1` | снимать экраны |
| `StepDelay` | `800` | пауза между шагами, мс |
| `CloseAfter` | `0` | закрыть кассу после прогона |
| `KeepOpenCheck` | `0` | не отменять чек, оставшийся открытым в конце |

`KeepOpenCheck` выключает страховку, а не включает функцию. По умолчанию
прогон отменяет чек, который остался открытым, — иначе он повиснет в базе.
Сценарию, который чек **оплачивает и печатает**, эта страховка только мешает:
там чек закрывается штатно.

### `[Scenario]`

Шаги нумерованные, формат `команда,аргумент1,аргумент2`:

| Команда | Что делает |
|---|---|
| `newcheck` | открыть новый чек |
| `item,<код>,<кол-во>` | пробить товар |
| `card,<номер>,<тип>` | приложить карту, тип см. ниже |
| `wallet,<баланс>,<ставка>` | задать баланс кошелька и % начисления |
| `bonus,<сумма\|max>` | запросить списание баллов |
| `walletapply` | применить списание и начислить по ставке |
| `pay,<сумма\|total>` | внести оплату; `total` — вся сумма чека |
| `print` | напечатать чек **эмулятором** (см. ниже) |
| `shot,<имя>,<форма>` | снимок: `main`, `fiscal` или без аргумента — активная |
| `wait,<мс>` | пауза |
| `log,<текст>` | запись в журнал |
| `state` | записать в журнал номер чека, итог и доступные баллы |
| `paywin` | открыть штатное окно оплаты наличными |
| `closepay` | закрыть окно оплаты |
| `ts,<команда>` | **не работает**, см. ниже |
| `cancel` | отменить чек |

У шага `log` весь остаток строки — это текст, запятые в нём допустимы.
У остальных шагов аргументов не больше двух.

Третий аргумент `shot` выбирает форму:

| Цель | Что снимает |
|---|---|
| `main` | главную форму — MDI-родителя |
| `check` | кассовую форму `fhvbb` |
| `wallet` | карту в мобильном кошельке |
| `fiscal` | окно чека эмулятора |
| `pay` | окно оплаты наличными |
| без аргумента | активную форму |

**Цель `main` для кассового экрана не годится.** Она снимает MDI-родителя, а
кассовый экран живёт в дочерней форме: сразу после закрытия модального окна
родитель ещё не перерисован и в кадр попадает пустой прямоугольник. Для
кассового экрана нужна цель `check`.

### Шаги кошелька: начисление и списание баллов

Сервис лояльности с тестовой машины недоступен, но касса и не ходит в него
напрямую: ответ сервиса разбирает `PKG_LOYALTY_UTIL.PREPARE_RESPONCE_JSON`.
Самопроверка подаёт в этот же вход ответ, составленный ей самой — работает
весь штатный путь, включая распределение списания по строкам чека.

Ничего в обход пакетов и ничего за пределами локальной `TMDB_LOYALTY_LOG`.

Порядок шагов внутри продажи важен:

```ini
5=card,3902925401573,6
6=wallet,0,5          ; баланс 0 лей, начисление 5%
7=bonus,5             ; попросить списать 5 лей
8=walletapply         ; применить списание и начислить
9=pay,total           ; платим уже уменьшенную сумму
10=print
```

`walletapply` идёт **до** `pay`: списание уменьшает суммы строк чека, и
только после него `pay,total` возьмёт правильную сумму.

| Шаг | Что делает |
|---|---|
| `wallet,<баланс>,<ставка>` | ответ `member`: баланс кошелька и процент начисления. Пустой баланс — оставить прежний |
| `bonus,<сумма\|max>` | `set_redeem`: сколько списать. `max` — предел `min(баланс, сумма чека)` |
| `walletapply` | ответ транзакции: списание из `bonus`, начисление `нетто × ставка / 100`, новый баланс |

**Баланс живёт между чеками внутри прогона.** Поэтому в серии продаж видно,
как он растёт от начислений и убывает от списаний — достаточно задать его
один раз в первой продаже:

```ini
; продажа 1 - задаём стартовый баланс
6=wallet,0,5
; продажи 2..5 - баланс переносится, задаём только ставку
26=wallet,,5
```

Сам алгоритм начисления и списания — в
bonus-algorithm.md.

### Шаг `ts` не работает — и вот почему

Замысел был такой: `ts,<команда>` вызывает `TFTS::ExecCmd` — диспетчер, через
который работают все кнопки тачскрин-интерфейса, — и одним шагом открывает
весь их набор.

**На практике шаг всегда завершается отказом.** Глобальный указатель
`FTS` в TS/TS.cpp объявлен, но **никогда не присваивается**:
экземпляры создаёт `TTSDispatcher::SetupTS`, принимая указатель **по ссылке**
и складывая его в собственный список:

```cpp
void TTSDispatcher::SetupTS(TFTS* &TS, int AInterfaceID, …)
{
  TS = new TFTS(Application);
  …
}
```

Единого экземпляра, до которого можно дотянуться извне, в проекте нет.

Чтобы шаг заработал, нужен доступ к списку диспетчера — это отдельная
доработка, а не настройка. Пока шаг честно пишет причину в журнал.

Операции, которые нужны в прогоне, добавляются отдельными шагами — как
`paywin` ниже.

### Шаг `paywin`: штатное окно оплаты

Открывает `Tfclose_bon` тем же путём, что и сама касса в
`Tfhvbb::ShowModalFormCloseBon`:

```cpp
if( !fclose_bon ) fclose_bon = new Tfclose_bon(Application);
fclose_bon->Show();
```

Разница одна: показ **немодальный**, иначе прогон встал бы на `ShowModal`.
Закрывается шагом `closepay`, снимается целью `shot,<имя>,pay`.

### Какой тип карты указывать

Тип уходит в `NCP_CARD.UseCardNcp` и решает, **где** касса ищет карту:

| Тип | Где ищется | Что это |
|---|---|---|
| `1` | `TMS_DCARD` по `card_type = 1` | старые дисконтные карты |
| `6` | `pkg_cards.get_card_by_barcode` → `MVMS_CARDS` | современные карты: лояльность, баллы, кошелёк, столовая |

Почти всегда нужен **тип 6**: баллы, кошелёк и типы карт (`MVMS_CARD_TYPES`)
живут именно там. Тип 1 — историческая ветка, во многих схемах в `TMS_DCARD`
нет ни одной активной карты, и касса ответит
`Cardul discont cu barcod ... nu e inregistrata!`.

Тип 6 дополнительно требует, чтобы программа Fidelitate была включена:
`FSEnabled` в параметрах и `div_flag = 1` в `VMS_POS_BY_DIV` для номера кассы
из `PosID`. Иначе касса скажет, что для этого магазина такие карты не
активированы.

Проверить карту до прогона:

```sql
select pkg_cards.get_card_by_barcode('3902925401573') from dual;
```

Пример:

```ini
[Scenario]
1=log,--- проверка продажи ---
2=shot,start
3=newcheck
4=item,16110,1
5=item,69297,2
6=shot,check-goods
7=card,3902925401573,6
8=bonus,max
9=shot,bonus
10=cancel
```

### Счёт баллов в базе: шаг `ledger`

Отдельная группа шагов для счёта баллов в Oracle
(loyalty-ledger.md). Работают независимо от внешнего
сервиса: всё происходит в той же базе, где живёт чек.

| Шаг | Что делает |
|---|---|
| `ledger,open,<карта>,<остаток в леях>` | завести счёт; если он уже есть — оставить как есть |
| `ledger,member,<карта>` | предъявить карту чеку: остаток из счёта, карта показывается в кошельке |
| `ledger,apply,<списание в леях>` | провести операцию; без суммы — списать максимум, который разрешают чек и счёт |
| `ledger,cancel` | отменить операцию по этому чеку |
| `ledger,state,<карта>` | остаток, под холдами, доступное |
| `ledger,reconcile,<карта>` | сходится ли книга движений с остатком |

Готовый сценарий полного цикла — `Win32\Debug\selftest-ledger.ini`. В нём
два чека, и это не случайность:

* **чек A** — списание, повтор и печать;
* **чек B** — списание и отмена.

Отмену нельзя проверить на том же чеке, что и печать: печать чек закрывает,
`OpenComand` обнуляется, и `ledger,cancel` честно отвечает «нечего». Первая
версия сценария была устроена именно так и отмену на деле не проверяла.

Повтор `ledger,apply` оставлен намеренно: он проверяет идемпотентность.
Второй вызов ничего не списывает, остаток не меняется, а в журнале и у
кассира появляется «Повтор: операция уже была проведена».

## Результаты прогона

Каждый прогон — свой подкаталог с датой и временем:

```
Win32\Debug\SelfTest\2026-08-27_19-42-15\
    selftest.log        журнал с отметками времени
    01-start.jpg        снимки по порядку
    02-check-goods.jpg
    03-card.jpg
    ...
```

Журнал пишет каждый шаг, суммы после каждого товара, доступные и
списанные баллы, а в конце — сколько шагов прошло и сколько с ошибками.
Если шаг упал, снимок экрана делается автоматически (`error-<номер>.jpg`).

## Оплата и печать чека

Полный сценарий продажи выглядит так:

```ini
17=pay,total
18=wait,1000
19=shot,06-paid,main
20=log,--- печать эмулятором ---
21=print
22=wait,2500
23=shot,07-receipt,fiscal
```

`pay,total` вносит всю сумму чека через `DTM->SetPaySum` — тот же путь, которым
пользуется форма закрытия чека. **Без оплаты `print` не сработает:** при
`CheckPay=2` касса отвечает `Suma nu este achitata integral!` модальным окном,
и прогон встаёт.

Печать идёт **только эмулятором**. Если текущий принтер не виртуальный, шаг
пропускается с записью в журнал: самопроверка не должна печатать настоящие
фискальные чеки. Что печатает эмулятор — см.
fiscal-emulator.md.

Оплаченный и напечатанный чек — это **закрытая продажа в базе**. Прогоны с
`pay` и `print` запускать только на тестовой схеме.

**Открытых чеков не остаётся.** Печать закрывает чек штатно; если сценарий
оборвался раньше, открытый чек отменяется в блоке завершения — кроме случая
`KeepOpenCheck=1`, когда его намеренно оставляют.

## Что мешает прогону чаще всего

Прогон идёт в реальном интерфейсе кассы, поэтому любое **модальное окно**
останавливает его насмерть: сообщение `cSelfTestRun` перестаёт обрабатываться,
шаги не выполняются, снимки не появляются. Журнал в этот момент обрывается на
последнем выполненном шаге — по нему и видно, где встали.

Поэтому в прогоне работает **сторож модальных окон**: таймер, который живёт и
внутри модального цикла. Он снимает окно, пишет его заголовок и текст в
журнал и закрывает — прогон идёт дальше. Ничего не прячется: снимки
называются `dialog-N.jpg`, а в конце журнала стоит «закрыто модальных окон: N».

Сторож строже, чем общее
автозакрытие окон ошибок: он закрывает **любое**
модальное окно, включая вопросы, — в автоматическом прогоне отвечать на них
некому.

Таблица ниже — про причины, которые лучше устранить, а не заглушить сторожем.

| Что видно | Причина | Что делать |
|---|---|---|
| `ORA-00918: столбец определен неоднозначно` при открытии `hvbb_comenz_restaurant` | вьюха `VMDB_COMENZ_RESTAURANT` схемы уже содержит `SUM_CREDIT`, а запрос при `MPPaymentCredit=false` добавляет свою такую же колонку | `MPPaymentCredit=1` в `[General]` |
| `REST request failed: Error getting Server Certificate` | фоновая синхронизация с сервисом лояльности не достучалась до сервера | `APISincronyzeOffline=false` |
| `Cardul ... nu e inregistrata!` | карта ищется не там — см. таблицу типов выше | тип `6` и реальный штрихкод из схемы |
| `Suma nu este achitata integral!` | шаг `print` на неоплаченном чеке | добавить `pay,total` перед `print` |

В ini одна и та же секция может содержать ключ дважды — Windows берёт
**первое** вхождение, а не последнее. Поэтому переопределять параметр надо
ближе к началу `[General]`, а не в конце файла.

## Где что лежит

| Файл | Назначение |
|---|---|
| `uSelfTest.h/.cpp` | весь механизм: чтение сценария, журнал, снимки, прогон |
| `uFiscalView.h/.cpp` | окно чека эмулятора, цель снимка `fiscal` |
| `ucLogin.cpp` | автовход в `ShowModal` |
| `fMenu.cpp` | запуск сценария после показа главной формы |
| `dtmod.h/.cpp` | константа сообщения `cSelfTestRun` |

Снимок делается через `TForm::GetFormImage()` и сохраняется в JPEG
(`Jpeg.hpp` уже используется в проекте).

Прогон запускается отложенным сообщением `WM_USER + cSelfTestRun`, чтобы
сначала завершилась обработка события показа формы, и ожидание внутри
шагов идёт через `Application->ProcessMessages()` — иначе интерфейс
замер бы и снимки вышли пустыми.
